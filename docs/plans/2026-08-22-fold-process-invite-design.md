# 过程折叠：新用户默认摊开 + 长任务当场邀请

> 2026-08-22。一次性 plan。完成后取舍升华进 `src/components/AIPANEL_SPEC.md`，本文件删除。

## 问题

`foldAgentProcess` 现在默认开（收起过程）。对天天用的人对味——那些步骤确实是打扰；但新用户第一次用旗鱼就只看到一行「读了 3 个文件 · 24s」，看不见它到底怎么把活干成的，最该"惊喜"的一刻被收进了折叠行里。

**过程折叠本身还没发版**，所以不存在"升级后突然被摊开"的兼容包袱——所有人都可以从"还没表态"开始，无需为存量状态做任何保全。

## 定稿形态

**默认摊开每一步，第一次遇到长任务时就地邀请他收起来；表过态的人再也不被问。**

### 三态语义（核心）

`foldAgentProcess` 从「开/关」两态改成「**开 / 关 / 还没表态**」三态，与 `agentOnboardingShown` 同样的手法：schema 里不给默认值，`undefined` = 还没表态。

三态不是为了兼容存量，而是因为**"没表态"和"明确说了要摊开"必须分得开**：前者还该被邀请一次，后者永远不该再被打扰。两者生效值都是摊开，光看生效值分不出来。

| 状态 | 界面表现 | 有资格被邀请 |
|---|---|---|
| `undefined`（新装） | 摊开全过程 | ✅ |
| `true` | 收成一行 | ❌ |
| `false` | 摊开全过程 | ❌ |

用户点过邀请里的任一按钮、或去设置里动过这个开关 → 落盘为显式 `true`/`false`，从此不再邀请。

**生效值 = `choice === true`**，只有一处真相（用户的表态）。前端现有的 `savedFoldAgentProcess ?? true` 必须删掉——那是第二处默认，改了后端就会对不上。

### ⚠️ 坑：默认值会被写进磁盘

`conf`（`electron-store` 底座）构造时会把 `defaults` 里文件中缺失的键**直接写盘**（`Object.assign({}, defaults, fileStore)` 后与文件比对，不等就落盘）。所以只要 `defaultConfig` 里还留着 `foldAgentProcess: true`，磁盘上就一定有这个键，`has()` 永远为真，**"还没表态"这个状态根本不会存在，邀请永远不出现**。

实测本机 `qiyu-terminal-config.json` 里 `foldAgentProcess: true` 已经在盘上了（无从判断是默认值写的还是手动开的）；而 `agentOnboardingShown` 不在盘上——它正是靠"不进 defaults"才守住了三态，代码里那句注释「故意不设默认值」说的就是这件事。

因此**必须把 `foldAgentProcess` 从 `defaultConfig` 里摘掉**，这是三态能成立的前提，不是可选优化。

### 不写迁移

没发版就没有存量用户，盘上带着这个键的只有开发机。为一次性清理留一个永久 migration（外加 schemaVersion 台阶和单测）不划算——**退出应用后手工删掉那一行再启动**即可。

> 已知副作用：任何跑过 dev 构建的机器，键还在盘上就等于"已表态"，邀请一次都不会出现。日后若有人报「邀请不出现」，先查这个键在不在，别去查判定逻辑。

### 什么叫"特别长"

不看时长，只看步数——跑三分钟只有两步的任务屏幕是安静的，没什么可烦；烦的是刷屏。

判定复用折叠算法已有的 pinned 语义，新增纯函数 `measureProcessRuns(steps)`（`src/utils/process-fold.ts`）：只数**最长连续非 pinned 段长度**与**累计非 pinned 步数**，不构造 `ProcessFoldView`。

> 注意：不能拿 `foldProcessSteps(steps, { enabled: false })` 的结果来判定——关闭时它返回单个 open 段，分段信息不存在。必须独立度量。

触发阈值（满足其一）：

- 单段连续过程 ≥ **20** 步
- 整个任务累计过程步数 ≥ **40** 步（防止过程被它的话切成很多小段、每段不到 20 但总量已巨大）

**这两个数是量出来的，不是拍的。** 用本机真实历史（358 个非联络会话 / 1900 个任务）跑同一套 pinned 判定，分布如下：

| 分位 | 最长闷头段 | 过程总步数 |
|---|---|---|
| p50 | 3 | 5 |
| p90 | 8 | 30 |
| p95 | 12 | 46 |
| p98 | 20 | 72 |
| max | 59 | 350 |

- 单段 20 已是 p98（1900 个任务里 39 个）。**不要再往上抬**：50 只剩 5 个任务命中，100 一个都没有——那条件等于白写。它爱边做边说，一开口段就断了，所以闷头段天生长不了。这条抓的是另一种难受：连续二十次动作一句话不说，人会怀疑它死了。
- 累计 40 命中前 6.8%，是实际起作用的那条。取 40 而非 30/35 是因为配额只有两次，误触一次就废掉一半。
- 样本来自重度开发用户，任务比新用户长得多；同样阈值放到新用户身上只会更难触发，因此偏保守是安全的方向，偏激进不是。

前置条件（全部满足才邀请）：

- 用户还没表态
- 非调试模式、非严格模式（这两种情况开了也不收，问了等于骗人）
- 非联络 tab（`tab.type === 'assistant' && tab.agentId === COMPANION_AGENT_KEY`，复用 `AiPanel` 同一判据常量）
- 邀请配额未用尽

度量只在前置条件全通过时才算，常态零开销。

### 邀请长什么样

对话流里的一个虚拟项（`VirtualItem.type = 'fold_invite'`），不是弹窗、不是 toast——toast 会飘走，用户正盯着输出根本来不及读。视觉与折叠行同源：无图标、无底色、左边缘与正文对齐。

```
它已经埋头做了 23 步了。以后把这些干活的过程收成一行？   收起来 · 我要看全过程
```

插在**当前任务最后一段过程之后**。任务还在跑时那一段就是流的尾巴，所以这一行自然跟着最新步骤往下走、始终在视线内；它开口说话后这段过程结束，邀请就固定在那儿。

点「我要看全过程」→ 原地换成一句淡确认：「好，以后都摊开。想改就去设置 → 对话显示」。必须给撤销的落点。

### 邀请配额

最多两次，且必须跨会话。落盘 `foldProcessInviteCount: number`（0/1/2）。

per-tab 内存里记 `inviteAnchorGroupId`：一旦某个 group 被选为载体就不再改，配额在选定那一刻消耗。因此**同一次会话期间这行一直在那儿**，滚回去还看得到；关掉会话重开则不再出现（配额已消耗，邀请本身不落盘，不是 step）。这是刻意的简化——唯一需要持久的是用户的表态。

### 点了「收起来」要当场看见效果

生效值一变，该任务所有过程段立刻收成一行。**不新做塌缩动画**——沿用既有「收起不做动画」的取舍，不为此引入新机制；但**必须把视口锚定到刚生成的那条折叠行**，让用户看到"刚才那一大段变成了这一行"，而不是在滚动里迷路。

这与过程折叠原有的「不让东西冒出来又消失」有张力：那条规矩防的是系统自作主张地变，用户自己按下开关时当场反馈是必需的。此例外要写进 SPEC，否则以后会被当 bug 修掉。

## 任务拆解

1. **三态**：从 defaults 摘掉该键。验收：`SFT_DATA_DIR` 指向空目录首启后 `qiyu-terminal-config.json` 里**没有** `foldAgentProcess`（证明 defaults 不再回写）；设置页手动勾一下再取消，键才出现且为 `false`。开发机上手工删掉存量的那一行以便自测。
2. **前端单一真相**：store 去掉 `?? true`，设置页开关照旧读写。验收：设置页勾选/取消后重启保持；未表态时开关显示为关。
3. **长过程度量**：`measureProcessRuns` + 单测。验收：构造 25 步连续过程命中单段阈值、19 步不命中；被它的话切成 5×9 段（累计 45）命中累计阈值、切成 4×9 段（累计 36）不命中。
4. **邀请行**：资格判定、虚拟项、两个按钮、配额消耗、滚动锚定。验收：新装跑长任务出现邀请；点「收起来」当场收且视口不乱；点「我要看全过程」出现确认；联络 tab / 严格模式 / 调试模式不出现；重开会话不再出现。
5. **文案与 SPEC**：中英同步 + 设计目标升华。

## 不做

不做「前几次摊开、之后偷偷收起」——替用户做决定还不告诉他，比现在更糟。不做覆盖层式气泡引导。不改 IM / 网关渠道（那边没有折叠这个概念）。不做单会话临时折叠开关（另一个功能）。不改后端步骤记录。
