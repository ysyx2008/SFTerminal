# 崩溃诊断 SPEC

## 设计目标

起因：11.6.0 的 Windows 用户反馈频繁崩溃——主程序闪退、子进程崩溃。翻遍日志找不出原因，因为原生层的崩溃根本不经过日志：进程直接消失，日志最后一行只是崩溃前的正常记录。

更要紧的是，我们对崩溃率完全是盲的。只有一个用户开口，我们无法判断这是个例还是普遍问题——「没人反映」和「没人崩溃」分不清。绝大多数用户崩了只会骂一句然后关掉软件，不会来找我们。

因此这个模块要解决的是四件事：

1. **崩溃要留下现场。** 包括那些不写日志的原生崩溃，事后要能还原出崩在哪里，而不是只知道「它崩了」。
2. **崩溃要能被计数。** 要能区分用户正常退出和程序异常退出，能回答「这台机器上崩了几次」。
3. **崩溃后主动找用户，而不是等用户翻设置页。** 只在设置页放个按钮，实际上没人会去点。
4. **交出现场的门槛要低到一次粘贴。** 主动作是复制一段可以直接发到群里的摘要文本，而不是让用户去目录里找文件、发几百兆的附件。完整诊断包是次动作，给愿意配合的用户用。

### 关键取舍

**主进程崩溃时弹不出窗，这是物理限制。** 那种情况下只能在下次启动时补报，所以「区分正常退出与异常退出」不只是为了统计，它是崩溃后补报的唯一依据。

**防打扰优先于上报成功率。** 面对一个已经被崩溃折磨到怀疑人生的用户，弹窗轰炸只会让他直接卸载。宁可少收几份报告，也不能让提示变成新的骚扰：同类问题短时间内只说一次，单次运行有提示上限，用户随时能关掉。

**用户看不见的部分不打断他。** 子进程崩溃在用户眼里是「某个功能坏了」，不是「软件崩了」，不该用模态弹窗打断他手上的活；只有界面真的不可用时才值得打断。

**复制出去的东西用户自己能看见，这就是最好的隐私说明。** 因此不再单独做诊断包内容预览界面——摘要就在剪贴板里，他一眼就知道自己交出了什么。

### 明确不做

- 自动上报到服务端、转发邮件。上报通道留着接口，本版不接——客户端里放邮箱密码等于公开密码，且大附件根本发不出去。
- 连续崩溃自动进入安全模式、自动降级功能。留待下一版。
- 卡死（界面无响应）的检测。用户口中的「崩溃」可能包含卡死，但那需要另一套手段。
- 上报前让用户逐项预览、勾选诊断包内容。

## 行为契约

**崩溃判定**

- 用户正常退出应用后，下次启动不得报告崩溃。
- 重复启动（已有实例在跑，新实例随即退出）不得被算成一次崩溃，也不得抹掉已有实例的崩溃计数。
- 程序异常终止后，下次启动必须报告上次崩溃，并给出连续崩溃次数。
- 一次正常退出即视为恢复正常，连续崩溃次数归零。
- 崩溃记录文件损坏或缺失时，按「首次启动、无崩溃」处理，不得因此启动失败。

**提示**

- 界面已经不可用时（渲染界面崩溃），提示必须仍然能出现，并提供当场恢复界面的动作，不要求用户重启应用。
- 提示要说清三件事：哪个部分崩了、影响什么、现在能做什么。不出现堆栈原文和错误码堆砌。
- 同一类问题在短时间内只提示一次，其余静默计入统计。
- 单次运行内提示次数有上限，超出只记录不打扰。
- 提示里能一键永久关掉崩溃提示，设置页能重新打开。

**交出现场**

- 复制出的摘要是纯文本，篇幅控制在能直接粘贴进聊天窗口的量级，包含版本、系统、崩溃类型、出错的具体部分、崩溃次数、显卡与驱动状况，以及崩溃前的少量相关日志。
- 摘要要能区分原生层崩溃与程序逻辑异常——这是判断问题性质最关键的一条信息。转储里能直接读出的性质（例如内存耗尽、访问违例）必须写进摘要一行，让人不用打开转储就能判断。
- 补报上次异常退出时，摘要里的日志必须来自上次那次运行，不能是这次启动之后新写的——否则看起来像崩在连外部服务，其实完全不是。
- 单条日志过长要截断，避免第三方整段堆栈把摘要撑到粘不出去。
- 完整诊断包可另行生成，包含日志、崩溃转储与环境信息。
- 诊断包体积有上限，不能因为崩溃转储攒得多而大到发不出去。

**隐私**

- 复制出的摘要、以及诊断包里的文本内容，都不出现主机名、系统登录用户名、家目录真实路径，以及常见形态的密钥。
- 脱敏依据是运行时已知的具体真实值，不靠猜测式的关键词匹配。唯一例外是形态明确、无歧义的密钥串：固定前缀加长串，以及网址查询参数里「参数名 + 长密钥」。不为此去读凭据库。
- 记录 AI 对话原文的调试日志不纳入诊断包。
- 诊断包里的崩溃转储是崩溃瞬间的进程内存快照，它无法脱敏，同时又是还原崩溃位置的唯一依据。所以界面上必须明说包里含它，不能让用户以为整个包都脱过敏；而「复制摘要」这条主路径不含转储，始终是干净的。

**不许拖慢应用**

- 崩溃记录的写入发生在崩溃现场，必须极轻，不能因为记录本身再拖垮一次退出。
- 日志收集与打包不得卡住界面。
- 崩溃记录不得无限增长。
